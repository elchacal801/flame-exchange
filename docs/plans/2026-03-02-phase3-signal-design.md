# Phase 3: SIGNAL (v0.5) — Ecosystem Integration Design

## Context

FLAME v0.4 (FORGE) delivered a queryable intelligence platform: static JSON API, MCP server, Sigma exports, D3 relationship graph, coverage assessment, and confidence scoring. Phase 3 transforms FLAME from a standalone platform into an interoperable node in the global fraud intelligence ecosystem by producing standard-format outputs (STIX extensions, MISP galaxy, TAXII-compatible feeds) and adding regulatory compliance mapping.

## Scope

All 5 roadmap items (3.1–3.10), with two scoping decisions:

- **STIX SDOs only** — skip SCOs (bank-account, payment-card, crypto-wallet, device-fingerprint). FLAME carries fraud patterns, not operational IOCs. SCOs can be added in a future extension when FLAME ingests real observables.
- **Static TAXII** — generate TAXII 2.1-compatible JSON files at build time instead of running a live server. Consistent with FLAME's static-first architecture. No infrastructure to maintain.

## 1. STIX 2.1 Fraud Extension (Items 3.1–3.2)

### Problem

No fraud-specific STIX extension exists. FLAME currently exports TPs as generic `attack-pattern` SDOs, losing fraud-specific semantics (scheme type, loss estimates, mule networks, monetization rails).

### Design

#### 4 New SDOs

**x-flame-fraud-scheme** — Represents a complete fraud lifecycle pattern.
- Properties: `scheme_type` (enum: ato, bec, synthetic-identity, etc.), `cfpf_phases` (list), `loss_estimate` ({low, high, currency}), `affected_sectors` (list), `kill_chain_phases` (CFPF mapping), `confidence_score` (int 0-100)
- One per Threat Path. Replaces the generic `attack-pattern` as the primary TP representation.

**x-flame-financial-transaction** — Models the fraudulent money movement pattern.
- Properties: `transaction_type` (wire/ACH/A2A/crypto/check), `amount_range` ({low, high, currency}), `rail` (SWIFT/FedWire/ACH/blockchain), `velocity_pattern` (description)
- Derived from P4 (Execution) and P5 (Monetization) phase content in each TP.

**x-flame-mule-network** — Models money mule infrastructure.
- Properties: `recruitment_method` (romance/employment/social-media), `geographic_spread` (list of regions), `estimated_throughput` (description), `network_type` (individual/organized/hybrid)
- Only generated for TPs that reference mule activity (TP-0011, TP-0001, etc.).

**x-flame-fraud-actor-profile** — Extends threat-actor with fraud specialization.
- Properties: `fraud_specialization` (list of fraud types), `monetization_methods` (list), `sophistication_level` (low/medium/high/expert), `jurisdiction` (list of regions)
- Derived from Underground Ecosystem Context sections where present.

#### 5 New Relationship Types

| Relationship | Source → Target | Meaning |
|---|---|---|
| monetizes | fraud-scheme → financial-transaction | How the scheme converts to financial action |
| launders-through | financial-transaction → mule-network | How funds are moved through mule infrastructure |
| impersonates | fraud-actor-profile → identity | Who the actor pretends to be |
| recruits | fraud-actor-profile → mule-network | Actor recruits mules |
| enables | malware/tool → fraud-scheme | Technical enabler of the scheme |

#### Implementation

- Update `scripts/export_flame_stix.py` to generate extended SDOs alongside existing attack-patterns (backward compatible — existing consumers still see attack-patterns).
- New SDOs use `custom_properties` dict with `x_flame_` prefix per STIX 2.1 custom object spec.
- Write `docs/STIX-FRAUD-EXTENSION.md` as the formal spec document.

### Files

| File | Action |
|---|---|
| `scripts/export_flame_stix.py` | Modify — add SDO generators, new relationship types |
| `docs/STIX-FRAUD-EXTENSION.md` | Create — extension specification |
| `database/flame_stix_bundle.json` | Rebuilt — now includes extended types |

## 2. MISP Galaxy & Feed (Items 3.3–3.5)

### Problem

The existing `attck4fraud` MISP galaxy is unmaintained (6 tactics). FLAME's 33 TPs, 50 fraud types, and 5 CFPF phases provide a much richer taxonomy that MISP users need.

### Design

#### Galaxy Definition (`data/misp/flame-galaxy.json`)

Standard MISP galaxy format:
```json
{
  "description": "FLAME Fraud Threat Paths - fraud schemes mapped across CFPF lifecycle",
  "icon": "fire",
  "name": "FLAME Fraud Threat Paths",
  "namespace": "flame",
  "type": "flame-fraud",
  "uuid": "<deterministic>",
  "version": 1
}
```

#### Cluster File (`data/misp/flame-cluster.json`)

One cluster value per TP (33 entries). Each entry includes:
- `value`: TP title
- `description`: TP summary
- `uuid`: Deterministic (same as STIX ID seed)
- `meta`: fraud_types, sectors, cfpf_phases, confidence_score, mitre_attack refs
- `related`: Links to MITRE ATT&CK galaxy entries via ATT&CK technique IDs

#### Automated Feed (`database/misp-feed/`)

Generated by new `scripts/export_misp.py`:
- `manifest.json` — Feed manifest listing all events with timestamps
- `{uuid}.json` — Per-TP MISP event file with attributes mapped from TP content
- Feed URL can be subscribed to by any MISP instance

#### Build Integration

Add `python scripts/export_misp.py` step to CI workflow after STIX export.

### Files

| File | Action |
|---|---|
| `scripts/export_misp.py` | Create — galaxy, cluster, and feed generation |
| `data/misp/flame-galaxy.json` | Generated |
| `data/misp/flame-cluster.json` | Generated |
| `database/misp-feed/manifest.json` | Generated |
| `database/misp-feed/{uuid}.json` | Generated (33 files) |
| `.github/workflows/build-and-deploy.yml` | Modify — add MISP export step |

## 3. Framework Mapping Navigator (Item 3.6)

### Problem

Analysts using different frameworks (CFPF, FT3, Group-IB, ATT&CK) need to see how FLAME's TPs map across their framework's stages. The current heat map only shows CFPF × fraud-type coverage, not cross-framework mapping.

### Design

#### UI

New wide modal triggered by a "Navigator" button in the header stats area (same icon button pattern as heat map, assessment, graph).

**Layout:**
- Framework tabs along the top: CFPF (default) | FT3 | Group-IB | ATT&CK
- Matrix: rows = 33 TPs (sorted by ID), columns = framework stages
- Cell color: green (3+ DL rules covering this TP×stage), yellow (1-2 rules), gray (mapped but no rules), empty (not mapped)
- Click cell → navigate to TP detail view
- Hover tooltip: TP title + stage name

**CSS Grid** rendering (not D3 — it's a table, not a graph). Horizontal scroll for frameworks with many stages (FT3 has 12, Group-IB has 10, ATT&CK varies).

#### Framework Stage Definitions

| Framework | Stages | Source |
|---|---|---|
| CFPF | P1-P5 (5 stages) | `cfpf_phases` frontmatter |
| FT3 | 12 tactics | `ft3_tactics` frontmatter |
| Group-IB | 10 stages | `groupib_stages` frontmatter |
| ATT&CK | Variable (tactics) | `mitre_attack` frontmatter → tactic lookup |

#### Export

- "Export SVG" — renders current matrix view as downloadable SVG
- "Export JSON" — ATT&CK Navigator layer format (only for ATT&CK tab)

#### Data Source

Reads from `FlameData.getData()` (index) for framework mappings. Detection rule counts from `FlameData.loadDetectionRules()` for cell coloring.

|---|---|
| `index.html` | Modify — add Navigator button + modal HTML |
| `app.js` | Modify — add `renderNavigator()` function, framework tab switching, SVG/JSON export |

## 4. Regulatory Compliance Mapping (Items 3.7–3.8)

### Problem

Organizations need to demonstrate that their fraud controls satisfy regulatory requirements. FLAME can map TPs to specific regulations, enabling a "which regulations does my coverage satisfy?" analysis.

### Design

#### Regulatory Requirements Config (`config/regulatory_requirements.yaml`)

~15-20 entries covering key regulations:

```yaml
- id: REG-PSD3-SCA
  name: "PSD3 Strong Customer Authentication"
  jurisdiction: EU
  category: authentication
  description: "Requires multi-factor authentication for electronic payments"
  relevant_fraud_types: [account-takeover, unauthorized-transaction, phishing]

- id: REG-UK-PSR-APP
  name: "UK PSR APP Reimbursement"
  jurisdiction: UK
  category: reimbursement
  description: "Mandatory reimbursement for APP fraud victims"
  relevant_fraud_types: [authorized-push-payment, impersonation, social-engineering]
```

Regulations to include: PSD3/PSR (EU), UK PSR APP reimbursement, FinCEN AML/BSA advisories, FATF Recommendation 16 (travel rule), MAS SRF (Singapore), Australia SPF, FFIEC guidance, CFPB Reg E.

#### TP Frontmatter

Add optional `regulatory_refs` field:
```yaml
regulatory_refs:
  - REG-PSD3-SCA
  - REG-FFIEC-AUTH
```

#### Build Pipeline

- Parse `regulatory_refs` from frontmatter
- Include in index JSON and content JSON
- Add to `validate_submission.py` (validate IDs exist in config)

#### Frontend

- **Detail view**: New "Regulatory" section showing badges for each mapped regulation with jurisdiction and description
- **Coverage assessment**: Add "Regulatory Coverage" output — given selected sectors/fraud types, show which regulations are satisfied by existing TPs

### Files

| File | Action |
|---|---|
| `config/regulatory_requirements.yaml` | Create — regulatory requirement definitions |
| `scripts/validate_submission.py` | Modify — validate regulatory_refs against config |
| `scripts/build_database.py` | Modify — parse regulatory_refs, include in exports |
| 33 `ThreatPaths/TP-*.md` files | Modify — add regulatory_refs where applicable |
| `Templates/threat-path-template.md` | Modify — add regulatory_refs field |

## 5. Static TAXII Endpoints (Item 3.9)

### Problem

Threat Intelligence Platforms (TIPs) like MISP, OpenCTI, ThreatConnect consume STIX bundles via TAXII 2.1 protocol. FLAME should be consumable without manual download.

### Design

Generate TAXII 2.1-compatible JSON files at build time in `api/taxii/`:

```
api/taxii/
  discovery.json          # TAXII discovery document
  default/
    collections.json      # List of available collections
    collections/
      flame-threat-paths/
        manifest.json     # Object manifest with versions
        objects.json      # STIX bundle (fraud-scheme SDOs)
      flame-detection-rules/
        manifest.json
        objects.json      # STIX bundle (course-of-action SDOs)
      flame-baselines/
        manifest.json
        objects.json      # STIX bundle (baseline SDOs)
```

**Discovery document** follows TAXII 2.1 spec: title, description, default API root URL.

**Collections** expose 3 collections with proper UUIDs, media types, and can_read/can_write flags.

**Object endpoints** serve the STIX bundles directly. No filtering/pagination (static files), but the full bundle is small enough (~300KB with extensions) to fetch in one request.

A TIP can be configured with the GitHub Pages URL as the TAXII root, enabling automated periodic sync.

### Files

| File | Action |
|---|---|
| `scripts/export_taxii.py` | Create — generate TAXII-compatible static files |
| `api/taxii/` directory | Generated (discovery + 3 collections) |
| `.github/workflows/build-and-deploy.yml` | Modify — add TAXII export step |

## Dependency Graph

```
Batch A: STIX Extension (3.1-3.2)
    │
    ├──→ Batch C: Static TAXII (3.9) [needs STIX bundles]
    │
    └──→ Batch B: MISP Galaxy & Feed (3.3-3.5) [uses STIX UUIDs]

Batch D: Regulatory Mapping (3.7-3.8) [independent]

Batch E: Framework Navigator (3.6) [independent]

Batch F: Rebuild + CI (all artifacts)
```

**Parallelism:** Batches D and E are independent of A/B/C and of each other.

---

## Batching Strategy

| Batch | Items | Dependencies | Parallelizable with |
|---|---|---|---|
| A | STIX Extension spec + export update | None | — |
| B | MISP Galaxy + Cluster + Feed | A (uses STIX UUIDs) | D, E |
| C | Static TAXII endpoints | A (serves STIX bundles) | B, D, E |
| D | Regulatory config + TP updates + frontend | None | A, B, C, E |
| E | Framework Navigator modal | None | A, B, C, D |
| F | Rebuild all artifacts + CI updates | A-E complete | — |

**Peak parallelism:** After Batch A, batches B, C, D, and E can all proceed in parallel.

---

## New Dependencies

None. All required libraries (stix2, pyyaml) are already in requirements.txt.

## Verification Strategy

After each batch:
- `python scripts/validate_submission.py` on all modified TPs
- `python scripts/build_database.py` succeeds
- `python -m pytest tests/ -v` passes
- Frontend: start dev server, verify new features, check for console errors

Final integration checks:
- STIX bundle validates against stix2 library's built-in validator
- MISP galaxy/cluster validate against MISP galaxy JSON schema
- TAXII discovery/collection files validate against TAXII 2.1 spec
- Framework Navigator renders all 4 framework views without errors
- Regulatory badges appear in detail view for mapped TPs
